# STEP 0 — Architecture Inventory

> Generated by reverse-engineering the repository for interview preparation.
> This is the starting map. Every subsequent evolution document uses this as ground truth.

---

## System Name
**GitChat RAG** — A Retrieval-Augmented Generation (RAG) system that lets users chat with any public GitHub repository.

---

## High-Level Architecture (3-Service Layout)

```
[Browser / React SPA]
        |
        | HTTP (axios, hardcoded localhost:3000)
        v
[API Gateway — Node.js / Express]   <—— stores chat history
        |                                 MongoDB Atlas
        | HTTP (axios)
        v
[AI Service — Python / FastAPI]
        |
        |—— MongoDB Atlas Vector Search (read: retrieve chunks)
        |—— Jina AI Embeddings API (read: embed query at runtime)
        |—— Groq LLM API (read: grade, rewrite, generate)
```

## Component Inventory

### 1. Frontend (`frontend/`)
| Component       | File                              | Role |
|-----------------|-----------------------------------|------|
| App             | `src/App.jsx`                     | Two-state router: Dashboard → ChatRoom |
| Dashboard       | `src/components/Dashboard.jsx`    | Repo URL input, triggers ingest |
| ChatRoom        | `src/components/ChatRoom.jsx`     | Chat UI, renders Markdown, shows sources + retry badge |

**No backend state management.** Session ID is generated client-side via `crypto.randomUUID()` and lives in a `useRef` — it is lost on page refresh. History is re-fetched from MongoDB on every new session.

---

### 2. API Gateway (`api-gateway/`)
| Layer  | File                               | Role |
|--------|------------------------------------|------|
| Entry  | `src/index.js`                     | Express server, MongoDB connect, CORS |
| Router | `src/routes/api.js`                | 3 routes (see below) |
| Model  | `src/models/ChatHistory.js`        | Mongoose schema + compound index |

**Routes:**
| Method | Path                  | What it does |
|--------|-----------------------|--------------|
| POST   | `/api/repo/submit`    | Proxies repo URL to AI service `/agent/ingest` |
| POST   | `/api/chat/message`   | Fetches last N history turns, calls AI service, persists exchange |
| GET    | `/api/chat/history`   | Returns raw history records for a `(repo_url, session_id)` pair |

**Key design choices visible in code:**
- `HISTORY_WINDOW = 20` — sliding window cap (10 exchanges) to avoid token explosion
- Compound index on `{ repo_url, session_id, created_at }` — designed for the exact query on line 41 of `api.js`
- No auth middleware — purely open, no JWT/session layer
- No job queue — `/repo/submit` is a **synchronous blocking proxy call** (ingest can take minutes)

---

### 3. AI Service (`ai-service/`)
| Layer       | File                    | Role |
|-------------|-------------------------|------|
| Entry       | `src/main.py`           | FastAPI app, Pydantic schemas, 2 endpoints |
| Ingest      | `src/ingest.py`         | Clone repo → chunk → embed → store in MongoDB |
| Agent       | `src/agent.py`          | LangGraph self-correcting RAG graph |

#### Ingest Pipeline (`ingest.py`)
```
clone_repo (gitpython)
    → get_directory_tree()  → injected as a special "structure" Document
    → load_documents()      → DirectoryLoader per extension (12 types)
    → filter BLOCKED_FILENAMES (lockfiles, .env)
    → RecursiveCharacterTextSplitter (chunk_size=2000, overlap=200)
    → cap at MAX_CHUNKS=2000
    → batch embed via Jina AI (batch=100, delay=1s)
    → upsert into MongoDB Atlas Vector Search
```

#### RAG Agent (`agent.py`) — LangGraph Graph
```
retrieve → grade_documents → [decide_to_generate]
                                    |
                    ┌───── relevant=True ────→ generate → END
                    │
                    └── not relevant + retries < 2 ──→ rewrite_query → retrieve (loop)
                    │
                    └── not relevant + retries exhausted ──→ generate (graceful degradation)
```

**4 Graph Nodes:**
| Node              | What it does |
|-------------------|--------------|
| `retrieve`        | Smart 3-tier search: structural keywords → filename pre-filter → score-filtered similarity |
| `grade_documents` | LLM call (Groq) to judge if chunks are relevant to the question |
| `rewrite_query`   | LLM rewrites the failed query with code-search-optimized language |
| `generate`        | LLM generates answer with full chat history context + source attribution |

**`GraphState` (TypedDict):**
- `question` — mutable (rewritten on retries)
- `original_question` — immutable (always used for final generation)
- `retry_count` — max 2 retries (`MAX_RETRIES = 2`)
- `is_relevant` — bool from grader
- `chat_history` — list of `BaseMessage` objects (injected from MongoDB on each request)
- `sources` — set of filenames attributed to the answer

## Database: MongoDB Atlas

**Two collections — one database (`codebase_rag`):**

| Collection   | Used by         | Purpose |
|--------------|-----------------|---------|
| `vectors`    | AI service      | Vector store — stores embeddings + chunk text + metadata |
| `chathistories` | API gateway  | Mongoose model (auto-named by Mongoose from `ChatHistory`) |

**Atlas Vector Search Index (`atlas_search_index.json`):**
- `numDimensions: 1024` (Jina `jina-embeddings-v3` output dimension)
- `similarity: cosine`
- Index name: `"default"`

## Key Architectural Constraints (Visible in Code)

1. **No authentication** — any user can ingest any public repo and chat
2. **No namespace isolation** — all sessions share one MongoDB `vectors` collection; re-ingesting a repo adds duplicates
3. **Synchronous ingest** — HTTP request blocks until the full clone → embed → store pipeline finishes (can be 60–300s)
4. **No streaming** — LLM response waits for full generation before returning to client
5. **Hard-coded API URLs** — frontend calls `http://localhost:3000` directly (no Vite env var)
6. **Client-side session ID** — lost on page refresh; no server-side session management

## Inferred Evolution Candidates (for STEP 2)

| # | Evolution | Trigger |
|---|-----------|---------|
| 1 | Basic RAG → Self-Correcting RAG (LangGraph) | Retrieved chunks sometimes irrelevant; needed retry + regrade loop |
| 2 | Flat Similarity Search → Smart 3-Tier Retrieval | Structural/directory queries returned wrong chunks |
| 3 | No History → Sliding-Window Chat Memory | Context-free answers for follow-up questions |
| 4 | Sync Ingest (blocking HTTP) → (future) Async Job Queue | Long ingest blocks the HTTP request; UI shows indefinite spinner |
| 5 | No Deduplication → (future) Namespace/Repo Isolation | Re-ingesting pollutes vector store with duplicate chunks |
